# 开发守则 — VideoGenResearch-deepseek

> **什么时候加载**：首次接手本项目必读。之后按需查。
> 本文档是**规则真源**。与 memory 冲突时以本文档为准；本文档与用户最新口头指示冲突时，以用户为准并**立刻回来改这里**。

## 0. 项目定位

Remotion + video-shotcraft 的**技术验证 + 技术调研**项目。
交付：调研报告 + 最小可跑 demo + **可复用 Python 模块**（后续 `Agent_VideoGen_Module` 的地基，
亦可作为 `DailyNewsAssistant` 的功能拓展）。

**不是**一次性宣传片脚本堆。任何"只把样片渲出来就结束"的做法都算失败。

```
调研 → 构建方案 → 方案讨论&调整 → 开发 → 测试 → debug&修改 → 代码审阅(人工) → git cmd(人工)
```

| 阶段 | 落盘位置 | 是否必须 |

**发现的问题写在对应 document，不写在代码注释里。**

## 2. 测试尺度（用户明确口径，禁止加码）

- 默认**只跑「本次改动对应的单测节点」**：`pytest tests/test_x.py::test_y`。
- **不做全量测试**，不做「顺手跑一下全部」。
- **必要且仅当「功能可行性验证」时**才做真实 LLM / 付费渲染 —— 目的是确保功能真的可用。
  这类渲染的开销**必须记入文档**（耗时、费用、算力）。
- 用户会**阶段性**点名做整体 review 与全功能测试。那是用户的触发权，不是 AI 的默认动作。
- 验收标准：**一条会从红变绿的 pytest 节点，或一条带预期输出的命令**。
  给不出验收手段 = 需求没定义清楚，先问，不要边做边猜。

## 3. 成本纪律（本项目最贵的资源是 token，其次是渲染算力）

实测规律：`成本 ≈ 上下文大小 × 轮数`，且**重读上下文的开销远大于生成输出**。据此：

1. **先 `grep` 定位，再局部 `read`**；**同一个文件不读第二遍**（读过就记住结论）。
2. **大范围翻查派子代理**，只要结论，不要把整个仓库读进主上下文。
   `video-shotcraft` 有 236.7 MB / 1284 项 —— 主上下文读它等于烧穿预算。
3. **改文件用 Edit，不写补丁脚本**。脚本改完，工具会把整个文件重新注入上下文。
   只有「同一模式改 10 处以上」才值得写脚本，且脚本里不要出现转义字符。
4. **不读不需要的文件**。文档按需加载，`00_INDEX.md` 是唯一入口，不要一次性读完 `docs/`。
5. **计划与进度必须落盘**。`/clear` 后只活在上下文里的计划就没了 ——
   重新考古实测要花十几轮。恢复方式：`memory/project.md` + `docs/00_INDEX.md`。
6. **不做「以防万一」的验证**。不做用户没要求的截图、重渲、全量回归、额外格式输出。
   每个动作都要能说出「为了验收哪一条」。
7. **渲染是最贵的一步**：先 `npx remotion still` 出单帧自检（秒级），
   确认无误再整片渲染（分钟级）。不要一上来就整片渲。
8. **一个阶段一个会话**。完成一个阶段后建议 `/clear`，靠落盘文件接续。

## 4. 代码规范

- 分层清晰，**功能封装独立**；上层调下层，**禁止反向依赖**。
- **前端/脚本零业务逻辑**：`scripts/` 只是薄壳，业务逻辑在 `src/videogen/`。
- **核心功能 / 跨层 API：中英双语注释**；内部 helper 单语即可。
- 注释**只写「为什么」，不写「是什么」**。判据：删掉它，三个月后有人会不会把代码改错？
  不会就删。**注释不要过于繁琐。**
- 单文件 **≤ 500 行**。
- 可调参数**从配置读，不写死在代码里**；密钥只从 `.env` 读，**终端输出一律打码**（用户会截屏）。

## 5. git 纪律

- **AI 绝不执行 `commit` / `push`**。
- 只把指令写进 `docs/git_commands.md`：**分步、按功能切分、内容清晰可读**。
- **不要一个大而全的 commit**；不要描述不清的 commit。
- 该文件是**一次性**的：覆写前先 `git log` 核对上一组已执行过。

## 8. 动画代码的常见坑（每一条都真踩过）

| 坑 | 症状 | 规则 |
|---|---|---|
| `interpolate` 区间不等长 | `inputRange (1) and outputRange (2) must have the same length` —— **只在渲染时炸，`tsc` 查不出来** | 单一时间点做渐变时必须补一个窗口：`interpolate(f, [start, start + 8], [0, 1])`，不要写 `[start]` |
| 图片被 `maxHeight` 压窄后，按宽度算的**百分比坐标**标注溢出 | 标注整条被 `overflow:hidden` 裁掉，或跑到图外 | 图要么完全按宽度定尺寸，要么按高度；**不要混**。百分比定位的浮层要求容器尺寸与图**严格一致**（`ScanAnnotate` 返工过） |
| flex 居中 + `position:absolute` 文字混用 | 文字叠在图上（`RadarReveal` 返工过） | 图文要成序排列（图在上、字在下）时**全程用绝对定位 + 相对图定位**，不要图用 flex、字用 absolute |
| 字幕带与镜头内容打架 | 镜头里最后一行内容压在字幕框上（`NumberRoll` 返工过） | 安全框必须**先把字幕带高度扣掉**：`layout.ts` 的 `safe.bottom` 额外 +180（竖屏）/ +120（横屏） |
| 垂直位置写死像素 | 竖屏卡片悬空在轴上方很远处（`TimelineTravel` 返工过）—— 换行让实际高度与横屏不同 | 高度不确定的元素用**边锚定**（`top: axis; transform: translateY(-100%)`）而不是算 `top: axis - 250` |
| 契约文档写了、代码没做 | 卡数区间在 `01_spec_schema.md` 与 prompt 里都有，校验器**漏了实现** → 中视频真实调用给 11 镜（限 10）却直接通过 | **契约写了就必须有代码兜底**；文档与 prompt 只是"告诉"，校验器才是"保证" |
| 宽幅图在竖屏按宽度撑满 | 整页截图（1280×544）竖屏撑满宽度后高度仍过大，把镜头文案推进图底并叠上字幕带（`PageSpotlight` 返工**两次**才收敛） | 宽幅素材在竖屏要当**引证小图**处理：宽高都显著收窄（本项目竖屏用 0.70 × 0.32），不是主视觉 |
| 旁白与画面文字重复 | 收尾镜的旁白本身就是 CTA，与 lockup 的字标+标语两处一起显示，既冗余又互相压 | **收尾镜不铺字幕带**（`CaptionTrack` 的 `excludeRanges` 按帧区间排除）。aesthetic-rules C1 明确要求「品牌收尾镜头除外，保持干净」 |
| **抽帧品检抽在动画中途** | 看到 `0.900 / 9.000 / 00%` 以为数字算错了，其实规格里是正确的 `0.344 / 0.186 / 64%` —— 抽的是镜内第 40 帧，而数字要到第 72 帧才锁完 | **抽帧要抽在「动画落定后」**：先算清该镜的锁定帧（`rowStart + (位数-1)*stagger + duration`），再换算成全局帧/秒去抽。`ffmpeg -ss` 用秒，注意换算 |
| 底层报错只看日志尾部 | `write EOF` 看像管道问题，真因 `Permission denied` 被截断在更上面 → 白查两轮 | 见到底层报错先**全量搜 `denied`/`failed`/`Error`**，不要只看尾部 |

> 这九条都属于「`tsc` 过、渲染才炸，或渲染不炸但看着不对」—— 所以**改完镜头必须出静帧看**，
> 这正是开发守则 §3.7「先出单帧再整片渲染」的另一半理由。
> 其中竖屏问题的共同点是：**横屏验过不等于竖屏成立**，两种方向都要出图。
